# ADR 0016 — Área de Logs (proposta)

- **Status:** Proposto (aguardando decisão de origem dos logs)
- **Data:** 2026-10-09
- **Referência de produto:** [Hyperping Logs](https://hyperping.com/logs) (alpha)

## Contexto

O North já organiza Clients → Environments → Groups → Connections/Accesses, abre sessões SSH/SQL/API in-app e monitora alcançabilidade TCP (`connection_health_events`). O que falta é um lugar para **ler e investigar logs** ao lado disso: quando um monitor cai, ver o que o servidor estava dizendo.

O Hyperping Logs é a referência: fontes com token e retenção própria, busca com sintaxe, live tail, contexto em um clique, views salvas, dashboards por template, aba de logs no incidente e export. Ele **não** é APM nem error tracking — o North também não deve ser.

Restrições do repositório que moldam a proposta:

- Roadmap diz "fora de escopo: agente remoto instalado nos servidores". Logo, a coleta tem que usar o que o North já tem (SSH, SQL, API) ou **receber** logs — nunca instalar nada no servidor.
- Hoje o `main` **não abre nenhum socket de escuta**. Receber logs muda a superfície de segurança (ver `docs/06-seguranca.md`).
- ADR 0006 diz: sem FTS5 até haver gatilho de migração. Logs são esse gatilho para *este* domínio.
- Segredos nunca em SQLite, nunca no índice de busca, nunca em export padrão.

## Origem dos logs — opções

| # | Origem | Como funciona | Prós | Contras |
|---|--------|---------------|------|---------|
| A | **Pull via SSH** | Connection SSH existente roda `journalctl -f -o json`, `tail -F <arquivo>` ou `docker logs -f` pelo `remote-exec-service` | Zero superfície nova, reaproveita vault/host-key/sudo, combina com a identidade do produto | Só enquanto o North está aberto; formato varia (precisa parser) |
| B | **Atividade do próprio North** | Normaliza `connection_health_events`, `workflow_runs`, `access_history`, histórico da API como linhas de log | Dados já existem; entrega valor na fase 0; é o "audit log" do roadmap | Não é log de servidor |
| C | **Ingestão local** | Servidor HTTP em `127.0.0.1` (HTTP JSON + OTLP `/v1/logs`); apps/shippers enviam com token por fonte | Paridade com o Hyperping; aceita Vector/OTel Collector | Nova superfície de rede; app remoto só alcança via túnel/rede local; só recebe com o North aberto |
| D | **Pull de Access** | Query SQL periódica numa tabela de logs; polling de endpoint de API | Reaproveita SQL Studio / cliente API | Polling, sem tempo real verdadeiro |
| E | Syslog TLS (6514) | Receptor syslog | Cobre appliances/Linux legado | Gestão de certificado; deixar para depois |

**Recomendação:** fase 1 = **A + B** (nenhuma porta nova). C entra na fase 2 com revisão de segurança própria. D e E sob demanda.

## Decisões propostas

1. **Modelo unificado de linha de log**, independente da origem: `ts`, `level` (numérico, 0=trace…5=fatal), `message`, `service`, `host`, `trace_id`, `span_id`, `attributes` (JSON). Origem A/C/D só diferem no *adapter* que normaliza para esse modelo — espelha o desenho de `ProtocolDriver`: o UI nunca conhece a origem.
2. **Banco separado** `north-logs.db` (ao lado de `north.db`), com migrations próprias. Motivo: volume e `VACUUM`/purga não devem tocar o inventário, e export/backup do inventário não carrega logs.
3. **Busca com FTS5** (tabela externa sobre `message`) + colunas indexadas (`ts`, `level`, `source_id`, `service`, `host`, `trace_id`). Atributos arbitrários via `json_extract`. Registrar em ADR 0006 que logs ativaram o gatilho de FTS5 *apenas neste banco*.
4. **Parser de query puro em `src/shared`** (testável, sem Node): texto → AST → SQL parametrizado no main. Gramática alvo (igual ao Hyperping): palavras, `"frase exata"`, `-exclusão`, `chave:valor`, `chave:(a|b)`, `level:>=warn`, `chave:>N`, atributos aninhados `a.b:c`, `trace_id:`.
5. **Retenção por fonte** (3/7/14/30 dias) + teto de tamanho por fonte; job de purga no main em lotes.
6. **Live tail** como push em lote (~250 ms) de main → renderer num canal dedicado, com pausa ao rolar/hover e contador de pendentes. Se o volume medido justificar, migrar para `MessagePort` por assinatura (regra do CLAUDE.md para fluxo contínuo).
7. **Segredos:** token de ingestão fica no vault (`credentialRef`); senha SSH resolve só no main; logs **não** entram no índice da command palette nem em export de inventário; export de logs é ação explícita.

## Modelo de dados (migration do banco de logs)

```
log_sources   id, kind('ssh'|'activity'|'ingest'|'access'), name,
              client_id?, environment_id?, group_id?,        -- escopo (opcional; fonte pode ser global)
              connection_id?, access_id?,                    -- origem A / D
              config_json,                                   -- comando, caminho, query, intervalo…
              ingest_token_ref?,                             -- origem C
              retention_days, max_bytes?, enabled,
              last_received_at, created_at, updated_at

log_entries   id INTEGER PK, source_id, ts INTEGER(ms), level INTEGER,
              message TEXT, service, host, trace_id, span_id, attributes_json
              INDEX (source_id, ts DESC), (ts DESC), (level, ts DESC), (trace_id)

log_entries_fts   FTS5(message, content='log_entries')       -- mantida por triggers

log_views     id, name, query, range_json, columns_json, created_at   -- até 50
```

Dashboards (fase 3) ficam como `log_dashboards` com definição declarativa (lista de gráficos em uma linha de query).

## IPC (ordem do contrato: channels → contract → preload → handler → hook)

`logs:source-list|create|update|delete|test` · `logs:search` · `logs:histogram` · `logs:context` (20 linhas no mesmo host / mesmo padrão / mesmo trace) · `logs:export` (CSV/NDJSON, teto 10 000) · `logs:view-list|save|delete` · `logs:tail-subscribe|unsubscribe` + evento `logs:tail-batch`.
Todos os payloads com Zod em `src/shared/types/logs.ts`; `.parse` nos handlers.

## UI

- Rota `/logs` + item na sidebar; fontes escopáveis pela árvore (`?env=`, `?group=`, `?source=`).
- Layout em três áreas, como o resto do app: **painel de filtros** (nível, serviço, host, fonte) · **lista virtualizada** com histograma acima · **painel de detalhe** da linha (atributos, contexto, copiar). Colunas escolhíveis por atributo.
- **Barra de busca**: reaproveitar a infra CodeMirror de linha única criada para `VariableInput` (destaque de tokens + autocomplete de chaves/valores). `/` foca a busca.
- **Eventos sobrepostos ao histograma**: quedas de `connection_health_events` e execuções de workflow — é o equivalente ao "incident overlay" do Hyperping e é o diferencial do North (já tem esses dados).
- **Aba "Logs" na conexão** (painel de detalhes): janela de 15 min antes até 5 min depois de cada queda, erros/warnings agrupados por mensagem.
- **"Copiar para IA"**: linha + contexto em Markdown.
- Estado de UI no Zustand só para layout; query/intervalo/linha selecionada na **URL** (compartilhável, como o resto do app).
- Dependência nova provável: lista virtualizada (`@tanstack/react-virtual`). Gráficos: SVG próprio no início, sem lib.

## Mapeamento Hyperping → North

| Hyperping | North |
|-----------|-------|
| Fonte com token/retenção | `log_sources` (token só na origem C) |
| Integrações Vercel/CloudWatch/… | Fora de escopo; entram via origem C (OTLP/HTTP) se o usuário apontar |
| Busca com sintaxe | Parser em `shared` + FTS5 |
| Live tail | Push em lote com pausa inteligente |
| Contexto em um clique | `logs:context` |
| Views salvas (até 50) | `log_views` |
| Templates de dashboard | Fase 3, templates por tipo de fonte |
| Aba de logs no incidente / war room | Aba na conexão + overlay no histograma |
| Export CSV/NDJSON, Copy for AI | Mesmo |
| MCP com `search_logs` etc. | Fora de escopo agora; o contrato IPC já separa busca do UI, então é viável depois |
| Preço por GB | N/A (local-first) |

## Fases

0. **Atividade do North** (origem B): modelo + banco + `/logs` com lista, filtros e busca simples. Valida o modelo sem rede nem SSH.
1. **SSH pull** (origem A): fonte por Connection, templates de comando (`journalctl`, `tail -F`, `docker logs`), live tail, retenção, histograma com overlay de quedas, aba na conexão.
2. **Ingestão local** (origem C): servidor em `127.0.0.1`, token por fonte no vault, limites de corpo/taxa, OTLP/HTTP + HTTP JSON (inclui NDJSON e payload tipo Logtail). Exige ADR/revisão de `docs/06-seguranca.md` antes.
3. **Views salvas, export, "Copiar para IA", dashboards por template.**
4. Sob demanda: pull de Access (D), syslog TLS (E), MCP.

## Riscos

- **Volume:** SQLite aguenta, mas só com inserção em lote, índices enxutos e purga em lotes; definir teto por fonte desde a fase 1.
- **Logs contêm segredos:** sem redação automática no MVP; avisar na UI e nunca exportar por padrão.
- **Comando SSH montado com caminho do usuário:** sempre quoting de shell; só templates conhecidos, sem comando livre na fase 1.
- **Só coleta com o app aberto:** deixar explícito na UI (indicador "fonte parada desde…"), pois o North não tem agente.
- **Tamanho do banco/performance de FTS5:** medir antes da fase 2.

## Decisões em aberto (precisam do dono do produto)

1. Fase 1 começa por A+B como recomendado, ou a prioridade é C (ingestão) para paridade com o Hyperping?
2. `north-logs.db` separado (recomendado) ou mesmo banco?
3. Fonte de logs pode ser **global**, ou sempre pendurada em Client/Environment/Group/Connection?
4. Logs entram no export/import de inventário? (proposta: não)
5. Nome da seção na sidebar e no manual: "Logs"?
